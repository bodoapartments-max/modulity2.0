# ADR-0003 — Workspace Evolution Planning Through Existing Automat BuildPlans

## Status

Accepted.

## Context

Step 9 planning could propose an initial operating system, but it did not model an existing Workspace as the primary planning input. Business expansion requests require semantic reuse, thing-versus-process decisions, concise rationale, ambiguity handling, and duplicate prevention without creating a second apply protocol or trusting provider output.

## Constraints

- Canonical configuration remains Entity Types, Modules, Worksets, Widgets, and Reports.
- Operational Entities and Records are not planning context by default and are never generated by evolution planning.
- Step 9.2 remains the only trusted configuration-write boundary.
- SAFE_UPDATE and destructive operations remain disabled.
- Type-level RelationshipDefinition remains deferred.
- Provider output is untrusted and bounded.

## Decision

Introduce an in-memory, versioned `WorkspaceSemanticModel` derived only from the bounded canonical `WorkspaceConfigurationSnapshot`. A provider-neutral `WORKSPACE_ARCHITECT` Agent consumes that model and a business request, producing a structured `WorkspaceEvolutionPlan` with REUSE, CREATE, CONNECT, CONFLICT, UNSUPPORTED, questions, warnings, and concise decision rationale.

The Evolution Plan compiles into the existing `AutomatBuildPlan` contract. Existing deterministic validation, classification, persistence, fingerprints, approval, stale-plan protection, trusted apply, lock, journal, audit, and notification remain authoritative and unchanged in role.

Semantic reasoning may recommend reuse, but only deterministic schema/reference classification determines whether canonical reuse is compatible. Incompatible same-code resources remain CONFLICT. Ambiguous or incomplete analysis is review-only and cannot be persisted for approval.

## Consequences

- Repeated requests converge on REUSE instead of duplicate resources.
- Core Entity Types are preferred for role/synonym concepts such as staff, vendors, clients, cars, and tools.
- Persistent things become Entity Type proposals; processes/events become Module proposals.
- Workspace text is data, not trusted instructions.
- Context truncation produces `ANALYSIS_INCOMPLETE` rather than silent assumptions.
- Existing plans remain compatible; the BuildPlan contract gains bounded optional Architect rationale/summary fields.
- Future provider adapters can implement the same contracts without changing trusted apply.

## Deferred

Calendar Engine, RelationshipDefinition, destructive migration, Entity instance generation, background workflows, vector search, and production subscription entitlement remain out of scope.
